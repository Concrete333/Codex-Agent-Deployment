# Revised-skill A/B results — 10 September 2026

The revised skill did **not** save money in this six-run diagnostic. Every run
completed and passed the frozen acceptance checks. All three skill participants
chose to work alone; no trial spawned a worker or called Claude.

| Task | A: no-skill solo | B: revised skill | Difference | Frozen acceptance, both |

| Interval repair | $0.263148 | $0.344366 | +30.9% | 13/13 methods, including 300 seeded interval comparisons |
| Catalogue investigation | $0.385036 | $0.501132 | +30.2% | 4/4 gates: exact findings, coverage/date, citations, unchanged source |
| Idempotency component | $0.678552 | $0.808176 | +19.1% | 29/29 checks |
| **Total** | **$1.326736** | **$1.653674** | **+24.6%** | **3/3 tasks each** |

Costs are captured standard API-equivalent estimates, not subscription charges
or allowance consumption. The six participants together used $2.980410 by this
measure. Preparation, the Sol High fixture-writing helper, supervisor turns and
offline evaluation are excluded. They are experiment overhead, not free work.

In the shared runner and private receipts, the revised-skill condition retains
the historical identifier **C**. It is **B in this two-condition report**;
the old unguided-delegation condition was not run.

## What the skill did

All three participants read the core skill, chose solo execution and skipped
the model-selection and Claude guides. That part of the revised routing worked.
No worker routing, delegation ownership, escalation, Claude execution or worker
waiting behavior was exercised by these six trials.

Both investigation participants wrote a standard-library script, then checked
its findings and citations. Both found 29 exposed services without valid waivers:
9 missing, 5 scope failures, 8 not started, 4 expired and 3 revoked. They reconciled
120 services and 102 finding citations. The 148 KB catalogue did not require
loading all its records into model context. This task therefore tested economical
tool use and the choice to remain solo, not the benefit of context-isolating
workers.

Both component participants reused the supplied validation helpers and existing
service integration, changing only the ledger and adding tests. The surrounding
package offered navigation context, but the actual implementation was contained.
It was not a large, independently distributed implementation workload.

## Concrete problems and a correctness distinction

### Generated-cache cleanup consumed useful budget

The skill component run initially ran tests without `-B`, creating Python cache
files. After passing tests and completing its source changes, it attempted a
recursive cache cleanup that the runtime rejected, listed the remaining files,
then issued a file-by-file cleanup command.

The three model responses issuing those cleanup commands used **$0.149736**,
about **18.5% of that run's total**. These are identifiable response costs, not
a claim that removing the detour would subtract exactly that amount from a rerun:
later context, caching and behavior would also change. No acceptance requirement
needed bytecode-cache removal. Avoiding generated artifacts at test invocation
or leaving irrelevant ignored caches alone is preferable to a cleanup loop.

### Not all additional review was wasted

The skill component participant noticed that an arbitrarily large positive
integer TTL can overflow when added to a float clock. It added a `Fraction`
fallback and a regression case. The baseline did not handle that case.

A **post-run diagnostic, outside the frozen score**, used `ttl_seconds=10**400`
with a constant float clock of `100.0`, then submitted the same request twice:

| Saved implementation | Result | Handler calls |
| --- | --- | ---: |
| A: solo baseline | `OverflowError: int too large to convert to float` on both calls | 2 |
| B: revised skill | Success followed by replay | 1 |
| Fixture reference | `ValueError: clock plus ttl_seconds must be finite` | 0 |

The published contract admits finite positive integers without a size bound.
This is a rare but valid case under that wording, and exposes a coverage gap in
the frozen checks and reference. It prevents claiming that all extra review was
pointless or that the saved implementations have identical correctness. It does
not establish a typical production benefit or justify a new general model ranking.
The original acceptance scores remain unchanged; the additional probe and exact
outcomes are reported separately, without model retries or implementation edits.

Future tasks should state practical numeric limits when those are intended, or
test the larger domain they actually promise. Do not silently narrow a contract
after seeing its results.

## Evaluation access repair

The two investigation graders initially failed before running checks: the
read-only sandbox could not read the oracle under the private `tempfile.mkdtemp`
preparation directory. This was a harness access problem, not an answer failure.

After all six trials ended, the frozen oracle and baseline catalogue were copied
byte-for-byte to a new temporary directory with normal inherited permissions.
Only the ignored local fixture paths were redirected; original paths and data
were retained. No ACLs, submitted files or grader assertions were changed.

The same grader then ran read-only against both original participant checkouts.
Both passed all four gates. Artifact hashes before and after grading match;
oracle/source-copy equality was checked before regrading. Original error logs
and results remain intact alongside separate `offline-regrade.json` receipts.
Future preflights should run reference grading through the actual sandbox route,
not only through the ordinary host interpreter.

## Implications to test next

1. **Make declining delegation cheap.** The core is still loaded in full before
   its early local-work decision. A short entrypoint with conditional operational
   guidance is a plausible next variant; merely reordering paragraphs cannot
   avoid loading them. Savings from this change have not been measured.
2. **Do not change worker rankings on this evidence.** None of the four worker
   families was used. There is no evidence here that one should replace another.
3. **Improve task selection before claiming delegation coverage.** These tasks
   were solvable cheaply by one agent and scripts. A future worker evaluation
   needs substantial independently checkable work—not just many files or a
   fixture that forces delegation.
4. **Keep verification tied to the contract.** Avoid unrelated housekeeping,
   but retain required correctness checks. Specify the acceptance domain before
   running, and validate the checker with counterexamples.

The operational skill was not changed during or after these trials. These are
recommendations for another controlled revision, not proven optimizations.
