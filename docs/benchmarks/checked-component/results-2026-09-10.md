## What happened

Both received the same component contract, starting source and independent
visible checker. The checker was also rerun externally from its canonical copy;
protected-file and checker hashes passed. Both changed only the ledger source
and added a test file. Neither needed a service change. Code inspection found
no material contract issue in the changed implementations; this is unblinded
model inspection, not proof of correctness on every possible input.

Both implementations use the supplied JSON validation, isolated payload/receipt
copies and overflow-safe deadline handling. They differ slightly in when they
perform clock validation and compute deadlines. The new checks cover the earlier
huge-integer failure, and both pass. Added-test counts are not quality rankings.

C read the 303-word core, skipped the operational/model references and chose to
keep the component local. Its explanation called this a tightly coupled change.
There were no descendants, Claude invocations, worker waits or polling loops.
This measures solo behavior with the policy and delegation tools present, not
the adequacy or savings of any worker configuration.

## One post-run correction, not a measured improvement

The tested core began “Keep small or tightly coupled work local,” but also said
a worker could own a settled component through implementation and tests. The
first instruction was too broad: dependent steps should stay with one owner,
but that owner need not be the coordinator. C's stated rationale made that
conflict worth correcting; it does not prove the instruction alone caused its
routing decision.

After both runs ended, the repo and installed core were changed to keep small
work local and tightly coupled work with one owner, explicitly permitting a
worker to own the whole component. The core is now 324 words. This clarification
has not been measured. No third trial, forced worker, task enlargement or silent
rerun followed this result.

The reduced entrypoint and independent checker did not demonstrate savings in
this pair. The next delegation experiment must distinguish the skill's routing
choice from worker performance; repeated solo outcomes cannot establish that
workers are ineffective. Any forced-worker control must be labeled separately.
